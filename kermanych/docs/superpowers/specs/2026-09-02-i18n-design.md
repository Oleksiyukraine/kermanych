# i18n layer — design

Status: approved (brainstorm), pending spec review
Date: 2026-09-02
Locales: `uk` (base, source of truth) + `en`

## Context

The Kermanych UI ships ~2,700 Ukrainian string literals across 95 files, all
hard-coded in templates, `.ts` registries and — at the server boundary — in
`packages/core` display functions and `apps/api` prose. There is **no i18n
scaffold today**: `apps/ui` has no `vue-i18n` dependency and `boot` is
`['tokens', 'tip', 'supabase']`. This spec introduces a two-locale layer
(`uk`/`en`) and defines exactly which string owner localizes where.

The task's premise ("Quasar, so i18n should already be there") is **false** —
this is greenfield.

## Decisions (locked in brainstorm)

1. **Locales:** `uk` is base and source of truth; `en` is a translation written
   as part of this work and reviewed by the user. `uk` is the fallback.
2. **Scope:** full transition in one feature branch (`feature/add-multilanguage`),
   parallelized by file-owner. No "half-localized" interim state.
3. **Server boundary — approach C (hybrid by string owner):**
   - `packages/core` pure display functions return **keys/structured data**; the
     UI renders text through the message catalog.
   - `apps/api` **notices + HTTP errors → codes on the wire** (`{ code, params }`);
     the UI maps codes to localized text.
   - **Model-facing** prompt text (`management-prompt.ts`, `release-notes-prompt.ts`,
     `limitation`) is **not** UI-localized; the user's locale is passed into the
     prompt so the model answers in that language.
4. **`session.name`:** left as-is (server keeps writing Ukrainian prose). No DB
   migration, no server dictionary. Names stay in the language they were created
   in. Rationale: minor label; everything daily-visible is localized.

## Non-goals

- No third locale, no per-account (Supabase) locale — locale is a **device**
  preference like the theme.
- No migration of the persisted `session.name` column, nor of historical
  transcript rows: old notices/names keep their stored language.
- No RTL, no locale-aware routing, no lazy per-route message loading (the whole
  catalog is small enough to ship in the bundle).
- No change to omp/model behavior beyond passing the locale into prompts.

## Architecture

### 1. UI infrastructure

- **Dependency:** `vue-i18n` (v9 or v10, whichever matches the app's Vue 3 minor;
  pinned in the plan).
- **`src/boot/i18n.ts`** — creates the i18n instance and installs it. Inserted in
  the boot array at position 1: `['tokens', 'i18n', 'tip', 'supabase']` (after
  theme, before anything that renders copy).
- **`src/lib/locale.ts`** — device-preference store, a direct mirror of
  `lib/theme.ts`: `STORAGE_KEY = 'kermanych.locale'` in `localStorage`, a reactive
  `locale` ref, `readLocale()` / `writeLocale()` / `initLocale()` (watches the ref,
  writes through, sets `i18n.global.locale`). Default `uk`. No server dependency.
- **Language switcher** — a control in Settings → `app-general` category, beside
  the theme toggle (same "on this machine, not the account" precedent). A plain
  two-option segmented control; no view-transition animation (a class/attribute
  flip suffices).
- **Formatting** — plurals, dates and numbers through vue-i18n's `Intl`-backed
  helpers, replacing ad-hoc formatting in `lib/time.ts` / `lib/calendar.ts` /
  `lib/format.ts` where those emit Ukrainian words.

### 2. Message catalog

- Per-locale, split by domain into typed TS modules (not one giant JSON), so keys
  are type-checked and reviewable file-by-file:
  `src/i18n/uk/{common,agents,board,settings,management,risk,kit,chat,errors,notices}.ts`
  and the parallel `src/i18n/en/…`, each locale aggregated by an `index.ts`.
- **`uk` is the schema**: vue-i18n's message-type is derived from the `uk` catalog,
  so a missing `en` key is a type error, not a silent runtime fallback.
- **Key naming:** `<domain>.<screen-or-group>.<element>`, e.g.
  `agents.launcher.title`, `kit.composer.send`, `settings.categories.projectBasics.blurb`,
  `risk.categories.technical`, `board.column.backlog`.

### 3. UI copy migration

- Every Cyrillic literal in `.vue` templates/scripts → `t('key')` / `$t`.
- **Data registries become key registries:** `lib/settings.ts`
  (`SETTINGS_SCOPES`, `SETTINGS_CATEGORIES` `{label,sub,blurb}`, `AGENT_KIND_LABELS`)
  and `lib/risk.ts` (`PROBABILITY_ANCHORS`, `IMPACT_ANCHORS`, `BAND_LABELS`,
  `RISK_CATEGORIES`, `RISK_KINDS`, `RISK_RESPONSES`, `RISK_STATUSES`,
  `RISK_EVENT_LABELS`, `PROXIMITY_LABELS`) hold **keys**; their `labelFrom` /
  `categoryLabel` helpers return keys, and callers render via `t()`. Because these
  helpers are pure and unit-tested, tests assert the **key**, not the prose.

### 4. Server boundary (approach C)

**core pure functions → keys/structure** (UI renders):
- `tool-display.ts` — the three stat strings (`каталог`; `${n} файлів[·обрізано]`;
  `${m} збігів / ${f} ф`) become structured `{ statKey, params }`; consumed by
  `KRequestBlock.vue` / `KLogBlock.vue`, which render via `t()`.
- `chat-blocks.ts` — the per-tool count units (`ln` / `збігів` / `файлів`) become keys.
- `agents.ts` — `AgentDef.label` (6: Ревізор, Промоутер, Провізор, Вирішувач
  конфліктів, Завершити, Саммарі) becomes `labelKey`; `agentById` callers that
  render (AgentSkillsPanel) use `t()`. The English `instruction` templates are
  unchanged (model-facing).
- `management.ts` — `MANAGEMENT_SECTIONS[].hint` and `.limitation` become keys for
  the UI (ManagementPage nav rail). Note: `limitation` is ALSO quoted into the
  model prompt — see model-facing rule below; the prompt reads the Ukrainian
  variant regardless of UI locale.

**api notices + HTTP errors → codes on the wire:**
- **Notice contract.** Extend the `TranscriptEntry` notice variant in
  `packages/core/src/types.ts`:
  `{ kind: 'notice'; id; at; level; text; code?: string; params?: Record<string,string> }`.
  `text` stays as the fallback (legacy rows, unmapped notices). Producers
  (`supervisor.service.ts` notice entries, `management-chat.service.ts` `turn.notices[]`
  — ~12-15 sites) set `code` + `params`. The UI renders `code`→`t('notices.<code>', params)`,
  falling back to `text` when `code` is absent/unknown. A `NoticeCode` union lives
  in core so producer and consumer share it.
- **HTTP-error contract.** The ~9-14 Ukrainian `BadRequestException` / `Error`
  messages (`management.controller.ts`, `release-notes.service.ts`,
  `management-chat.service.ts` timeouts) carry a stable `code` (+ `params`) in the
  response body; the UI's api client maps `code`→`t('errors.<code>', params)` for
  the toast, falling back to the server message. Codes are a shared `ApiErrorCode`
  union in core.

**model-facing text → locale in prompt (not UI-localized):**
- `management-prompt.ts` (rule ґ: "відповідай мовою користувача…") and
  `release-notes-prompt.ts` stay server-side Ukrainian **templates**; the caller
  passes the user's locale so the model produces output in that language. No client
  i18n for these. The locale reaches the api via the request (WS/HTTP), same channel
  the chat already uses.

**session.name:** unchanged. `supervisor.service.ts` keeps writing `чат …`,
`гілка: …`, `ревізія: …`. Inventory-only; explicitly out of scope.

### 5. Data flow

- **Locale selection:** switcher → `lib/locale.ts` ref → `i18n.global.locale` +
  `localStorage`. On boot, `initLocale()` restores it before first render.
- **Notice render:** api emits `{ code, params, text }` → UI `buildChatBlocks` →
  `KLogBlock`/`KPanel` render `t(code, params)` or fall back to `text`.
- **Error render:** api throws `{ code, params }` → UI api client → toast
  `t('errors.<code>', params)` or fall back to message.
- **Model call:** UI sends `locale` with the chat/release request → api injects it
  into the prompt.

### 6. Error handling

- **Missing message key:** dev build treats it as a type error (uk schema); at
  runtime vue-i18n falls back to `uk` then to the key string — never a blank.
- **Unknown notice/error code:** UI falls back to the server-provided `text`
  (uk). No screen ever shows a bare code.
- **Legacy transcript rows / session names:** render their stored `text`/name
  verbatim (uk). Expected and acceptable per the C decision.

### 7. Testing

- **core** (`packages/core/test`): existing `tool-display` / `chat-blocks` /
  `agents` / `management` tests updated to assert the returned **keys/structure**
  instead of prose. A `NoticeCode`/`ApiErrorCode` exhaustiveness test.
- **ui** (`apps/ui/test`): `lib/locale` unit tests (default, persist, switch);
  `lib/settings` / `lib/risk` key-registry tests (helper returns key). No component
  tests exist in `apps/ui` — the switcher + a spot-check of migrated screens is a
  **visual smoke** (`/kit` + a page) via the dev server, plus a lint check that no
  Cyrillic literal remains in migrated `.vue` files.
- **api** (`apps/api/test`): tests asserting the thrown `code` for the migrated
  exceptions; a notice-producer test asserting `code`+`params`.
- **en completeness:** a test (or type check) that every `uk` key has an `en`
  counterpart.

### 8. Components / units

New:
- `apps/ui/src/boot/i18n.ts`, `apps/ui/src/lib/locale.ts`,
  `apps/ui/src/i18n/{uk,en}/*` + `index.ts`, a language-switcher component (or
  inline in the `app-general` settings pane).
- `packages/core/src/i18n-codes.ts` (or extend `types.ts`): `NoticeCode`,
  `ApiErrorCode` unions + the notice variant's `code`/`params`.

Changed (by area — full list enumerated in the plan):
- core: `tool-display.ts`, `chat-blocks.ts`, `agents.ts`, `management.ts`, `types.ts`.
- api: `management.controller.ts`, `release-notes.service.ts`,
  `management-chat.service.ts`, `supervisor.service.ts` (notice codes only),
  `management-prompt.ts` / `release-notes-prompt.ts` (accept locale).
- ui: 95 files with copy (pages, components/kit, layouts, lib registries,
  composables/stores) + the renderers of core/api output
  (`KRequestBlock.vue`, `KLogBlock.vue`, `KPanel.vue`, api client, toasts).

## Decomposition & rollout

One branch, but implementation is ordered so parallel work never blocks on a
missing contract:

1. **Foundation (serial, first):** vue-i18n + `boot/i18n.ts` + `lib/locale.ts` +
   empty domain catalogs + switcher. The wire contracts: `NoticeCode`,
   `ApiErrorCode`, the notice variant change in core `types.ts`. Nothing renders
   differently yet.
2. **Server boundary (parallel after 1):** core pure-fn key refactor;
   api notice-codes + error-codes; prompt locale plumbing. Each is an independent
   package.
3. **UI copy migration (parallel after 1):** by area/file-owner subagents — one
   owner per file, no two agents touch the same file. Each area extracts `uk`
   keys and writes `en`.
4. **`en` review + completeness pass (serial, last):** user reviews translations;
   the completeness test gates merge.

Validation (build, typecheck, tests, visual smoke) runs once at the end, not
per-subagent, so parallel migration never blocks on each other's edits.

## Risks

- **Scale (~2,700 strings):** mitigated by file-owner parallelism and the uk-schema
  type gate (a dropped key fails the build).
- **Authored, not clerical copy:** the Ukrainian is authorial (e.g. settings
  blurbs); `en` must be *written*, not machine-translated — hence the explicit
  user review gate on `en`.
- **Notice/error code churn:** keeping `text` as a fallback means a missed producer
  degrades to uk prose rather than breaking — safe, incremental.
- **Model prompt locale:** if the locale is not threaded to a prompt call, the
  model answers in uk (rule ґ default) — a soft failure, not a break.
