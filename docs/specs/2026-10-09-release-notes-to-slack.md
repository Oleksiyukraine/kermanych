# Release notes → Slack, posted as the member who sends them

## Goal

A release note generated in a workspace can be sent to a Slack channel from the Release
Notes screen with a **«Send to Slack»** button. The message is posted **under the sending
member's own Slack name** (not a bot), and the channel is a per-workspace setting of the
Release Notes section.

## Context

- Release notes are generated by the local API (`ReleaseNotesService`) and stored by the
  browser in `workspace_release_notes` (member read/write). The screen is
  `apps/ui/src/pages/ManagementReleasesPage.vue`; a note opens in a modal with Edit/Copy.
- The Slack integration (`docs/specs/2026-10-05-slack-integration.md`) is a documentation
  Q&A **bot**: one Slack app per Kermanych workspace, bot + app-level tokens in each
  machine's registry SQLite, a cloud row `workspace_slack_integrations` with addresses only.
  A bot token can only post as the bot.
- The desktop app already runs a loopback OAuth round trip for GitHub sign-in:
  `src-electron/oauth-loopback.ts` listens on `127.0.0.1:53170`, opens the system browser
  and hands the `code` back to the renderer (`window.kermanych.startOAuth`).

## Decisions

- **Post with a Slack user token (`xoxp-`), obtained per member by OAuth v2 with PKCE.**
  Slack attributes `chat.postMessage` made with a user token to that user — the message is
  theirs, no «APP» badge. Slack accepts `http://localhost` redirects without a client
  secret once the app has PKCE enabled («desktop redirects», user scopes only), so the
  existing loopback listener can catch the redirect and the local API exchanges the code
  with the verifier — no secret, no server.
  - Rejected: the bot with `chat:write.customize` (name + avatar override). It still shows
    «APP», and only members who hold the bot tokens on their machine could send.
  - Rejected: pasting a user token. Slack shows a user token only to app collaborators who
    installed the app; an ordinary member has no way to get one.
- **Same Slack app as the Q&A bot.** The manifest gains user scopes `chat:write`,
  `channels:read`, `groups:read`, the redirect `http://localhost:53170/callback` and
  `pkce_enabled: true`. An app created from the older manifest must re-apply it. Token
  rotation stays off, so the user token does not expire.
- **The channel is a separate cloud row**, `workspace_release_notes_slack` (member read,
  owner write, no secrets): Slack app Client ID, team, channel. Separate from the Q&A row so
  a workspace can send release notes without running the Q&A bot. Owner-only like every
  integration binding — which channel speaks for the workspace is the owner's call.
- **The Client ID lives in that row.** It is public (it appears in every authorize URL)
  and every member's connect flow needs it.
- **User tokens are local**, `slack_user_tokens(workspace_id, user_id, …)` in the registry
  SQLite — the Jira/Linear/Slack custody rule. Validated against the row's Slack team.
- **The channel list comes from the owner's own token**: channels the owner is a member
  of. Posting as a member requires that member to be in the channel; Slack's
  `not_in_channel` is reported as «join the channel in Slack first».
- **Format.** The note's markdown goes through the existing `toSlackMrkdwn` (headings →
  bold, `**` → `*`, links) and `splitForSlack` (3,500 characters). The first part is the
  channel message; any further parts are replies in its thread, so one note is one message
  in the channel.
- **The API reads the note itself** (by id, under the member's JWT) and checks it belongs to
  the workspace, rather than trusting a body sent by the browser.
- **Desktop only.** The connect flow needs the Electron loopback; the browser build says so.

## Changes

- **Cloud:** migration `20261009090000_release_notes_slack.sql` —
  `workspace_release_notes_slack`, RLS member select / owner insert-update-delete, touch
  trigger. `packages/cloud`: `ReleaseNotesSlack` type, `getReleaseNotesSlack`,
  `upsertReleaseNotesSlack`, `deleteReleaseNotesSlack`, `getWorkspaceReleaseNote`.
- **API:** `slack/slack-oauth.ts` (PKCE pair, authorize URL, redirect constant);
  `SlackClient`: unauthenticated `oauth.v2.access`, `userIdentity`, top-level
  `postMessage`; `slack/slack-release-notes.service.ts`; registry table
  `slack_user_tokens`; routes in `http/slack.controller.ts`:
  `GET|DELETE /slack/account`, `POST /slack/account/authorize`, `PUT /slack/account`,
  `GET /slack/account/channels`, `PUT /slack/release-notes`,
  `DELETE /slack/release-notes/:workspaceId`, `POST /slack/release-notes/send`.
- **UI:** the manifest moves to `lib/slack-manifest.ts` (shared by the Integrations tile and
  the new settings); `stores/release-slack.ts`; `components/releases/ReleaseSlackModal.vue`
  (channel settings + this member's Slack account); a «Slack» button in the Release Notes
  toolbar and «Send to Slack» in the note modal; `releaseSlack.*` i18n in en/uk.
- **Docs:** README — a «Sending release notes to Slack» part of `### Slack`.

## Verification

- `apps/api/test/slack-release-notes.spec.ts` (new, 9 tests, real `SlackClient` and
  in-memory registry against a stubbed `fetch`): PKCE challenge matches RFC 7636 Appendix B
  and Slack's guide example; the code exchange sends the verifier of the URL handed out,
  with no token and no secret; an account from another Slack team is refused; a note is
  one channel message in Slack markup, as the member's token; a long note continues in
  that message's thread; a note of another workspace is refused; `not_in_channel` becomes
  «join it in Slack first»; an account of another team is refused at send.
- `pnpm --filter @kermanych/api test` — 870 passed; the only failures are the two in
  `test/rpc-session.compact.spec.ts`, untouched and failing before this change.
  `@kermanych/ui test` (52 files, 576) and `@kermanych/cloud test` — pass.
- Typecheck: `@kermanych/api` reports only `jira.controller.ts:350` and `@kermanych/ui`
  only `test/runtime-messages.spec.ts:13` and the unbuilt `@kermanych/api` import in
  `src-electron` — none in files this change touches.
- HTTP smoke on a preview api (compiled, `KERMANYCH_PREVIEW=1`): the app boots with the new
  service wired; `GET /slack/account` → `{connected:false}`; `POST /slack/account/authorize`
  → a `slack.com/oauth/v2/authorize` URL with `user_scope=chat:write,channels:read,groups:read`,
  `redirect_uri=http://localhost:53170/callback`, S256 challenge; a malformed Client ID and a
  code without a started flow → 400 with the messages above.
- UI on the preview dev server, state injected through Pinia (the preview has no cloud):
  the toolbar's «Slack» / «Slack · #releases» button, the settings modal (lead, channel
  facts, account box with the desktop-only hint, owner steps, Client ID field, remove), and
  «Надіслати в Slack» in the note modal. Pressing it reached the api and showed the api's
  error («not signed in», no cloud in a preview) as a toast.
- Not verified: a real Slack consent and post. It needs a Slack app with PKCE enabled and a
  signed-in desktop app. That `http://localhost` counts as a desktop redirect without a
  client secret is taken from Slack's PKCE guide, not observed.
