# Documentation answers in plain language

## Goal

When someone asks Kermanych about a feature and the answer comes from the project
documentation, the answer must be understandable by a non-technical person: simple, clear
words about what the feature does and how to use it, not a dump of technical data.

## Context

Two places answer questions from the documentation index, each with its own prompt:

- The Slack documentation bot — `buildSlackAnswerPrompt` in
  `kermanych/apps/api/src/slack/slack-prompt.ts`.
- **Менеджмент → Project Documentation** chat — `docsProtocol()` in
  `kermanych/apps/api/src/management/management-prompt.ts`.

Both told the model to answer only from the retrieved fragments and to be concise, but said
nothing about the reader. The documentation is written for engineers, so answers echoed its
file names, endpoints, tables and config keys.

## Decisions

- **A prompt rule, in both places.** The answer is generated by the model, so the reader is
  named in the prompt that writes it. The two prompts already mirror each other's rules, so
  both get the same one.
- **Describe what the user sees, not how it is built.** Screens, buttons and steps; no code,
  file names, functions, endpoints, tables or config keys.
- **Technical detail on request.** A question that asks for an endpoint or a setting still
  gets it, with a plain explanation of what it means — refusing would make the bot useless
  for the engineers in the same channel.
- **Citations stay.** The Slack `_Sources:_` line and the management chat's `kdoc:` links
  are how a reader opens the source; they are separate from the prose.
- Rejected: post-processing the answer to strip technical terms. It cannot tell a term the
  question asked for from one it did not, and it cannot rewrite a sentence into plain words.

## Changes

- `slack-prompt.ts` — new rule 6 (plain words for a non-technical reader); later rules
  renumbered.
- `management-prompt.ts` — `docsProtocol()` gets the same bullet in Ukrainian.
