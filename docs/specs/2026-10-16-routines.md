# Routines: scheduled tasks in Менеджмент

- **Date:** 2026-10-16
- **Scope:** `packages/core` (schedule and action vocabulary, occurrence math), `supabase/migrations`
  (two tables), `packages/cloud` (data access), `apps/api` (the scheduler and the three
  executors, Slack posting to a chosen channel), `apps/ui` (the «Routines» section, its store,
  toasts), README.
- **Builds on:** `docs/specs/2026-10-09-release-notes-to-slack.md`,
  `docs/specs/2026-10-12-multi-project-release-notes.md`.

## Goal

The operator asked (session `feature/scheduled-tasks`, 2026-10-16) for **routines** — scheduled
tasks in the Менеджмент tab, at the workspace level and at the project level. A routine runs
something the app already does, at a date and time, once or on a recurring schedule. The worked
example: generate release notes for a workspace every week and post them to a chosen Slack
channel. The operator also asked for a reference implementation to model the feature on.

## Reference

Two products from Anthropic define the shape, and Kermanych has one runner modelled on each:

| | Claude Code **routines** (cloud) | Claude Desktop **scheduled tasks** (local) | Kermanych, `cloud` runner | Kermanych, `local` runner |
|---|---|---|---|---|
| Runs on | Anthropic's cloud, fresh clone | your machine, app open | Supabase Edge Function, code from GitHub | the author's machine, app open and signed in |
| Definition stored | claude.ai account, private | `~/.claude/scheduled-tasks/`, private | the workspace's Supabase, **visible to the team** | the same |
| Schedule | hourly / daily / weekdays / weekly / cron, one-off | manual / hourly / daily / weekdays / weekly | manual / once / hourly / daily / weekdays / weekly / monthly | the same |
| Missed runs | — (always on) | one catch-up for the most recent miss in 7 days | — (always on) | the Desktop rule |
| Acts as | the owner's GitHub and connectors | the local user | the workspace: its GitHub token, Anthropic key, Slack bot | the author: their JWT, Slack token, plan |
| History | run list; green = started, not succeeded | run list including skipped runs | run list including skipped runs | the same |

Sources: <https://code.claude.com/docs/en/routines>,
<https://code.claude.com/docs/en/desktop-scheduled-tasks>.

Kermanych executes locally — worktrees, `omp` children and Slack user tokens never leave the
machine (README «The shared board») — so the first delivery had only the local runner, the
Desktop model. The cloud runner came second, on request, with the costs decision 11 lists.

## Context

- **Release notes** are generated by `ReleaseNotesService.generate` (local git log + one-shot
  child) and stored in `workspace_release_notes`. Today the browser stores them; the chat drives
  the same store.
- **Slack**: `SlackReleaseNotesService.send` posts a stored note as the member, with their user
  token (`slack_user_tokens`), to the one channel in `workspace_release_notes_slack`.
- **Launching an agent** from the api is already done by Jira and Linear: `createTask(cloud, …)`
  under the member's JWT, then `SupervisorService.createSessionFromTask(taskId, userId)`.
- **The api writes the cloud under the member's JWT** (`AuthService.cloudClient()`): Slack,
  Jira, Linear, doc indexing, task status. RLS is the authorization surface.
- **Read-only workspace one-shots**: the Менеджмент chat resolves the workspace's repositories
  with `managementRepos` / `managementCwd` and gives its child `MANAGEMENT_TOOLS`
  (read, grep, glob).
- **Timers**: the supervisor reaper and `CloudSyncService` use `setInterval`/`setTimeout` with
  `unref()`.

## Decisions

1. **Definitions in the cloud, execution on the author's machine.** A routine is a row in
   `workspace_routines`, readable by every member. It runs only in the api of the member who
   created it (`created_by`), while Kermanych is open and signed in. It acts with that member's
   JWT, Slack token, repository checkouts and agent subscription — the way a Claude routine acts
   as its owner.
   - Rejected: any online member runs it (a lease, like the Jira poller). Another member's
     machine may not have the repository bound or a Slack token, and a Slack message would appear
     under whichever name happened to be online.
   - A server runner (Edge Function + `pg_cron`) was rejected at first: it cannot read a local
     checkout, spawn `omp`, or hold a Slack user token, and the project had no service role key by
     design. The operator then asked for routines that run with nobody online and accepted those
     costs, so it became the second runner (decision 11). The local runner stays.
2. **Three kinds of run, chosen by scope and action.**

   | Scope | Action | What a run does | Slack |
   |---|---|---|---|
   | workspace | release notes | generates a note over one or more projects (branch each), stores it in Release Notes | optional |
   | project | release notes | the same, over that one project | optional |
   | workspace | prompt | a read-only one-shot over every workspace repository (Менеджмент's tools); the answer is the run's report | optional |
   | project | prompt | files a task card with the prompt and launches an agent session in the project, as ▶ on «Дошка» does | no — the result is in «Агенти» |

   - The release-notes period is the last *N* days up to and including the day of the scheduled
     time, in the routine's time zone (`periodDays`, 1–92). A run with no commits in the period is
     **skipped**, not failed — a quiet week is not an error.
   - A project prompt's card is assigned to the author and can be hidden from the board (the
     launcher's «Приховати з дошки»). If the launch fails, the card is deleted, so a failing daily
     routine does not fill the backlog.
   - Rejected: Deep analysis for project prompts. It interviews the operator, and nobody is there.
3. **Schedules**: `manual` (only «Run now»), `once` (date + time; switches itself off after it
   fires), `hourly` (minute), `daily`, `weekdays` (Mon–Fri), `weekly` (chosen days), `monthly`
   (day of month; clamped to the last day of a shorter month), each at a wall-clock time in the
   routine's IANA time zone (the author's, stored on the row). Rejected: raw cron. The presets
   cover the asks, and a cron string is a second vocabulary to validate and explain.
4. **When a run is due.** The api checks every minute and once shortly after sign-in. A routine
   is due when its latest occurrence at or before now is later than `armed_at` and at most 7 days
   old. Only that latest occurrence runs — a daily routine closed for a week runs once, as a
   **catch-up**. `armed_at` is reset by the database whenever the schedule or time zone changes
   or the routine is re-enabled, so an edit never fires a past time.
5. **Exactly once.** A run is claimed by inserting `workspace_routine_runs` with a unique
   `(routine_id, scheduled_for)`. The author signed in on two computers, or a restart, cannot run
   one occurrence twice: the second insert is a unique violation and is dropped. Manual runs have
   no `scheduled_for` and are not deduplicated.
6. **One run at a time per machine.** Runs are queued, the way the Slack bot queues answers, so
   scheduled work never spends the plan in parallel. An occurrence that comes due while the same
   routine is still running is recorded as **skipped** (Desktop does the same).
7. **Who may do what.**
   - Any member creates a routine; every member sees every routine and its history.
   - Only the **author** edits it or presses «Run now» — it speaks as the author.
   - The author or the **workspace owner** pauses, resumes or deletes it. The owner cannot edit
     another member's routine: the database trigger refuses a change to what it does by anyone
     but the author.
8. **Slack target per routine**: a channel the author is a member of, picked from their own
   Slack account (the release-notes OAuth flow), defaulting to the workspace's release-notes
   channel. Stored on the routine as team id, channel id and channel name. A routine can post to a
   channel other than the release-notes one. A Slack failure after a note was stored fails the run
   but keeps the note.
9. **Notifications**: the api emits `routine_run` over the existing socket when a run starts and
   when it ends. The UI shows a toast when it ends (and a native notification while the window is
   unfocused), and the Routines screen refreshes.
10. **The assistant does not write routines.** The section is `read` with a limitation; creating
    a schedule from the chat is out of scope.
11. **A cloud runner, chosen per routine** (asked for after the first delivery: «routines run
    even if the application is not active and the author is offline»). The operator picked it
    over a self-hosted «team runner» machine and accepted its three costs: the service role, an
    Anthropic API key billed per use, and Slack posts from a bot.
    - `workspace_routines.runner`: `local` (decisions 1–10) or `cloud`. The editor defaults a new
      routine to `cloud` when the workspace's cloud runner is set up. Changing the runner is
      content (author only) and re-arms the schedule.
    - **Trigger**: `pg_cron` calls `public.routines_cloud_tick()` every minute, which `pg_net`-
      posts to the `routines-runner` Edge Function with a shared secret read from Vault. The
      function claims due runs with the same due rule and unique claim, and runs each claimed run
      in its own invocation (its own wall-clock budget, 130 s by default on the free plan). A run
      still `running` after 15 minutes is failed as `routine_cloud_timeout`.
    - **Identity**: the function uses the service role — the one exception to the caller-JWT rule,
      confined to Supabase's runtime. Member actions (`status`, `configure`, `slack-channels`,
      `run-now`) first prove membership/ownership/authorship with the caller's own JWT.
    - **Keys** live per workspace in `workspace_routine_cloud`, with no grant to any client role:
      an Anthropic API key (and the model, picked from the key's own list), a read-only GitHub
      token, and optionally the workspace's Slack bot token. The owner sets them; the function
      checks each against its service before storing; members see only which are set.
    - **What a cloud run does**: release notes from the GitHub commits API (merges dropped, dates
      on the routine's clock, quiet projects left out) and a workspace report, both written by the
      Anthropic Messages API with read-only GitHub tools (`list_files`, `read_file`,
      `search_code`) in a bounded tool loop that forces the answer when turns or time run out. A
      project prompt only files its card for the author — the cloud has no checkout for an agent.
      Slack posts come from the bot, to channels it was invited to.
    - **One set of rules**: the schedule math (`packages/core/src/routine-schedule.ts`), both
      prompts and the Slack formatting are import-free modules copied into
      `supabase/functions/_shared/` by `scripts/sync-edge-shared.mjs`; a test fails when a copy is
      stale. Rejected: a second implementation in Deno or SQL, which would drift.
    - A note written by the cloud keeps its routine's author: the release-notes touch trigger now
      keeps the inserted `created_by` when — and only when — there is no caller.
    - Rejected: a self-hosted runner machine (keeps the security model, but needs a box online),
      and «any online member runs it» (does not cover nobody being online).

### Out of scope

- API/webhook and GitHub-event triggers (Claude routines have them; Kermanych has no public
  endpoint).
- Handing a routine to another member; running an agent session in the cloud.
- Slack for project prompts; a stored report for an agent session.
- Editing routines from the Менеджмент chat.

  `RoutineSlackTarget`, `RoutineRunStatus`, `RoutineRunTrigger`, `RoutineRunReason`;
  `validateRoutine` / `parseRoutineSchedule` / `parseRoutineAction` / `parseRoutineSlack`, each

- **Cloud:** migration `20261016090000_workspace_routines.sql` — `workspace_routines` and
  `workspace_routine_runs`, RLS (member read; member insert of routines; author/owner update and
  delete of routines; author-only insert of runs; runner-only update of runs; no delete of
  runs), touch triggers (author-only content edits, `armed_at`, project in the same workspace,
  run provenance frozen, `workspace_id` copied from the routine). `packages/cloud/src/routines.ts`:
  list, list runnable, get, create, patch, delete (refusal detected), list runs, claim (unique

  - `http/routines.controller.ts`: `POST /routines/:id/run`.

  - `SlackReleaseNotesService.postToChannel`: `send` now shares its posting.

  - A calendar-clock rail icon, `api.runRoutine`, `orchestrator.lastRoutineRun` with a toast and
