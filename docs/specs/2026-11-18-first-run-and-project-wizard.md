# Перший запуск: вітальний екран і візард проєкту

## Goal

Запит оператора (2026-11-17): новим користувачам важко зрозуміти, що й до чого в Керманичі.
Починаємо з самого початку — людина вперше встановила застосунок:

1. Що вона бачить одразу і чи зрозуміло, куди йти — запропонувати створити воркспейс.
2. Повністю переробити створення проєкту: лишити простий спосіб (≈ як зараз), а основним
   зробити повноцінний візард — назва, тека, куди клонувати, репозиторій, колір, одразу
   `GIT_TOKEN`.

Ширша тема «розуміння продукту» (пояснення на екранах, карта Керманича, ЦУК як довідник) —
наступна специфікація; тут лише перший запуск.

## Context

- **Перший запуск зараз** (`apps/ui/src/layouts/MainLayout.vue`): вхід через GitHub → модалка
  «Оберіть ШІ-провайдера» (без пропуску) → автовідкриття чеклиста «Розпочати»
  (`stores/onboarding.ts`, `components/onboarding/OnboardingChecklist.vue`, макет
  `design/onboarding.html`): 13 карток у 4 групах, перша дія «Створити воркспейс» — одна з них.
  Позаду модалки центр «Агентів» каже «Виберіть воркспейс або проєкт у перемикачі вгорі…»
  (`i18n/uk/index.ts:264`), хоча вибирати нічого. Закритий чеклист не лишає підказки, що далі.
- **Неправильні підказки чеклиста:** «Додати проєкт» — «⚙ → Проєкт → Основне» (насправді «+» на
  рядку воркспейсу в сайдбарі); «Прийняти або відкотити» — «Провізор відкриває PR», «▶ ⚖ ✓ у
  хедері сесії».
- **Створення проєкту зараз** — модалка в `MainLayout.vue` (`openCreateProject` /
  `submitCreate`): назва, «Git remote (необовʼязково, лише довідково)», платформа. Проєкт
  створюється в хмарі неприв'язаним; «Керманич нічого не клонує». Тека прив'язується окремо
  (`KDirPicker` → `PUT /api/projects/:id/bind`), `GIT_TOKEN` — у Налаштуваннях → `.env`
  (`PUT /api/projects/:id/env`), колір — у налаштуваннях проєкту.
- **Клонування в API немає.** Механізм передачі токена в git є: `worktree.service.ts:159-173`
  дає `GIT_TOKEN` як credential helper (`username=x-access-token`) через змінні оточення, без
  запису на диск.
- **Контракт токена:** інструкції агентів (`packages/core/src/agents.ts:200-264`) читають
  `GIT_TOKEN` з `.env` кореня worktree, куди Kermanych копіює `.env` проєкту (`carryFiles`); API
  для пушу й перевірки PR читає той самий файл (`supervisor.service.ts:3992`).
- **Хмарні колонки вже є:** `projects.color`, `default_branch`, `git_remote_url`, `platform`
  (`packages/cloud/src/projects.ts`). Міграція не потрібна.

## Decisions

1. **Хто новий користувач — два шляхи.** Розуміння, з чого почати, — персональне; підготовка
   проєкту — раз на проєкт, хто перший його прив'язав. Запрошений колега не бачить чужих кроків
   як «своїх виконаних» і не отримує пропозиції переналаштувати готовий проєкт.
   Відхилено: *лише «перший у команді»* і *лише «запрошений»* — обидва реальні.

2. **Вітальний екран замість порожнього центру.** Акаунт без жодного воркспейсу після вибору
   провайдера бачить у центрі «Агентів» (на весь центр, не модалкою) два шляхи:
   - **«Створити воркспейс»** — модалка воркспейсу (назва), а одразу за нею — візард першого
     проєкту в новому воркспейсі;
   - **«Мене запросили в команду»** — email цього акаунта з кнопкою «Скопіювати» і пояснення:
     передайте його власнику воркспейсу, він додасть вас у налаштуваннях воркспейсу → Учасники.
     Коли запрошення приходить (список воркспейсів оновлюється), екран сам переходить у
     наступний стан.

   Той самий центр веде далі за станом, поки людина не має з чим працювати:
   - є воркспейс, немає проєктів → «Створіть перший проєкт» → візард;
   - є проєкти, жоден не прив'язаний на цій машині → «Вас додали до «Y»» зі списком проєктів і
     «Підключити» біля кожного → візард у режимі «Підключити» (рішення 7).

   Чеклист у цей час сам не відкривається. Відхилено: *модалка чеклиста з одним кроком* — та
   сама модалка поверх порожнього екрана; *один наскрізний візард від входу* — змушує
   запрошеного створити зайвий воркспейс.

3. **Візард проєкту — чотири кроки.**
   1. **Доступ до git.** Поле `GIT_TOKEN`, посилання «Створити токен на GitHub» (fine-grained;
      права Contents RW, Pull requests RW, Metadata R), «Використати токен з проєкту X», коли на
      машині є прив'язаний проєкт з `GIT_TOKEN` у `.env`. Перевірка — `GET https://api.github.com/user`:
      «Токен належить @login» або помилка. «Пропустити» з попередженням «без токена агент не
      зможе пушити й відкривати PR».
   2. **Репозиторій**, три вкладки:
      - «GitHub» — репозиторії за токеном (`GET /user/repos`, з пошуком); без токена вкладка
        пояснює, що потрібен крок 1;
      - «За URL» — HTTPS або SSH, будь-який хостинг;
      - «Вже є на цій машині» — вибір теки (`KDirPicker`); з git читаються `origin`, поточна
        гілка й назва теки; крок клону пропускається. Тека, що не є git-репозиторієм, —
        відмова з причиною.
   3. **Куди і як.** Батьківська тека (за замовчуванням — батьківська тека вибраного проєкту,
      якщо він прив'язаний, інакше останнього створеного прив'язаного: час прив'язки реєстр не
      зберігає; без них — `~/Projects`, яку клон створить; вибір теки, відкритий на неіснуючій
      теці, починає з домашньої), підсумковий шлях `<тека>/<repo>` (відмова,
      якщо він існує й непорожній), назва (з назви репозиторію), колір, платформа (Web /
      Back-end / Mobile / «Не визначено»), гілка за замовчуванням (з `HEAD` remote, можна
      змінити). Для «Вже є на цій машині» — лише назва, колір, платформа, гілка.
   4. **Створення** — прогрес етапами (рішення 6), у кінці «Проєкт готовий» і «Поставити першу
      задачу».

   Відхилено: *одна довга форма* — новачок бачить усі ~10 полів одразу; *автовизначення
   платформи за файлами репозиторію* — окремі евристики з помилками, людина вибирає сама.

4. **Токен — у `.env` проєкту, як зараз.** Візард пише `GIT_TOKEN` у `.env` кореня теки. Якщо git
   цю теку не ігнорує (`git check-ignore .env` повертає не 0), візард дописує `.env` у
   `.git/info/exclude` — локальне правило, не комітиться, чужий `.gitignore` не змінює. Так агент
   не закомітить токен у першому PR. Повторне використання — через «Використати токен з проєкту
   X» (читається `.env` іншого прив'язаного проєкту), без нового сховища.
   Відхилено: *токен рівня машини в Keychain (`safeStorage`)* — друге місце секрету, переробка
   всіх читачів і копіювання в кожен worktree; *лише `.env` без захисту* — ризик витоку.

5. **Простий спосіб лишається, вхід — через візард.** «+» на рядку воркспейсу (і «Створіть
   перший проєкт») відкриває візард; на кроці 1 внизу — посилання «Швидке створення: без теки на
   цій машині», яке відкриває нинішню модалку (назва, remote, платформа) без змін у поведінці.
   Відхилено: *меню з двох пунктів під «+»* — новачок вибирає між незрозумілими варіантами;
   *лише візард із вкладкою «Без коду»* — половина кроків пропускалась би за умовою.

6. **Порядок кроку «Створення»: клон → хмара → прив'язка → `.env`.**
   - Клон не вдався — у хмарі нічого немає; показується вивід git; помилка автентифікації
     (401/403, `Authentication failed`) пропонує «Повернутися до токена», решта — «Спробувати ще
     раз».
   - Хмара не вдалася — клон лишається, «Спробувати ще раз» не клонує вдруге.
   - «Скасувати» під час клону зупиняє `git clone` і видаляє лише теку, яку створив візард;
     наявних тек візард не видаляє ніколи.
   - Поки йде клон, модалку не закрити (лише «Скасувати»).
   - Токен у клон іде тим самим credential helper, що в `worktree.service.ts`; після клону
     `origin` лишається без токена в URL.
   Відхилено: *спершу хмара* — збій клону лишає команді неприв'язаний проєкт-сироту;
   *паралельно зі спільним відкатом* — складніше без виграшу.

7. **Запрошений колега — той самий візард у режимі «Підключити».** Крок 1 — токен; крок 2 —
   «Склонувати `<remote проєкту>`» або «Вже є на цій машині» (попередження, якщо `origin` теки не
   збігається з remote проєкту; порівняння без схеми, `.git` і різниці HTTPS/SSH); якщо remote
   у проєкту немає (створений простим способом) — «За URL» і «Вже є на цій машині», а введений URL
   зберігається в проєкт. Крок 3 — лише батьківська тека; назва, колір, платформа — проєкту, лише
   для перегляду. Хмарний проєкт не створюється, крок 4 — клон → прив'язка → `.env`. Візард
   відкривається скрізь, де зараз відкривається вибір теки для неприв'язаного проєкту: вітальний
   екран, перший «Запустити», налаштування проєкту, картка чеклиста.
   Відхилено: *вибір теки + кнопка «Склонувати»* і *візард лише на вітальному екрані* — два
   різні процеси одного акту.

8. **Чеклист «Розпочати» без групи «Підключіть свій код».** Лишаються «Запустіть першого
   агента», «Навчіть Керманича», «Підключіть команду». Пункт у сайдбарі з'являється, коли на
   машині є прив'язаний проєкт; автовідкриття прибрано (його роль у вітального екрана).
   Неправильні підказки виправляються за поточним UI. Відмітки `ack` старих карток групи
   `connect` (`token`) ігноруються.
   Відхилено: *лишити як є* — дубль візарда; *прибрати повністю* — поки пояснень на екранах
   немає, група «Запустіть першого агента» корисна.

## API (нове)

- `POST /api/git/inspect` `{ path }` → `{ isRepo, origin?, branch?, name }` — для «Вже є на цій
  машині».
- `POST /api/git/remote-head` `{ url, token? }` → `{ defaultBranch }` — `git ls-remote --symref
  <url> HEAD` з credential helper; 15 с.
- `POST /api/git/clone` `{ url, parentDir, dirName, token? }` → `{ jobId }`; прогрес і результат
  — socket-подія `git_clone` (`{ jobId, phase, percent?, error?, path? }`, розбір `--progress`
  stderr); `POST /api/git/clone/:jobId/cancel`. Відмова до старту, якщо `<parentDir>/<dirName>`
  існує й непорожня.
- `POST /api/github/token-check` `{ token }` → `{ login }` і `POST /api/github/repos` `{ token }` →
  список (`full_name`, `clone_url`, `private`, `default_branch`) — через `github-client.ts`; токен
  лише в тілі запиту (не в URL, щоб не потрапив у логи), іде лише в API GitHub, не логиться.
- Захист `.git/info/exclude` — частина наявного `PUT /api/projects/:id/env`, коли пишеться
  `GIT_TOKEN`, тож він діє і для поля `GIT_TOKEN` у Налаштуваннях.
- «Використати токен з проєкту X» — `GET /api/projects/:id/env` (вже є).

## Edge cases

- Токен для не-GitHub хостингу: перевірки немає («не перевірено»), вкладка «GitHub» недоступна.
  `x-access-token` як username підходить GitHub; GitLab приймає будь-який username з PAT
  [INFERENCE — перевірити під час реалізації]; Bitbucket потребує `x-token-auth` — якщо так,
  username береться за хостом.
- SSH URL: токен для клону не потрібен (ключі людини); для PR він однаково потрібен — попередження
  кроку 1 лишається.
- Офлайн: кроки 1–2 показують помилку мережі; «Вже є на цій машині» працює без мережі, хмарне
  створення — ні (наявна поведінка `projects.create`).
- Браузерна збірка (не Electron): усе йде через API, `KDirPicker` працює так само.
- Два воркспейси, жоден проєкт не прив'язаний: вітальний стан «Вас додали до…» перелічує проєкти
  всіх воркспейсів, згруповані.

## Verification

- Превʼю з порожнім реєстром (без `KERMANYCH_SEED`): вітальний екран, обидва шляхи, скриншоти.
- Візард: клон публічного репозиторію за URL; приватного з токеном (кроки 1→4); «Вже є на цій
  машині»; скасування під час клону (тека видалена); помилка автентифікації → «Повернутися до
  токена»; `.env` у `.git/info/exclude`, коли `.gitignore` його не має.
- Тести API: розбір прогресу `git clone`, відмова для непорожньої теки, cancel прибирає лише
  створену теку, захист `exclude` ідемпотентний.
- Документація: README «Start here» і «Workspaces, projects and tasks» — новий перший запуск,
  візард, режим «Підключити», нові маршрути.
