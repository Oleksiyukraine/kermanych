# «Синергія»: fast prototyping on the live app, then «Імплементувати»

- **Branch:** `feature/add-synergy-prototyping-mode`
- **Scope:** `packages/core` (session marker, instructions, checkpoint chronology, brief),
  `apps/api` (launch without a card, tool restriction, slot exemption, checkpoints, restore,
  implement), `apps/ui` (the «Синергія» page, picks and URL on every request, checkpoint strip),
  i18n `uk` / `en`, `kermanych/README.md`.
- **Status:** decisions agreed with the operator in the deep-analysis interview (2026-11-06);
  waiting for the go-ahead to implement.

## Goal

The operator wants to build a feature by talking to the running app: «прибери кнопку А»,
«перемісти елемент ліворуч», «перенеси пункт меню в іншу секцію», «додай сторінку зі списком
замовлень», by text, by voice, with the ◎ pointer, and see each change in seconds. They try
variants and roll back. When the result is right, «Імплементувати» hands everything to a regular
agent, which builds it properly (backend, tests, i18n, docs).

A regular agent session already does all of this, but slowly. A simple change takes minutes,
because the agent runs a heavy model, follows the skills (task-spec, test, librarian), the
docs-policy line and its own habit of verifying everything. «Синергія» is the same machinery
with all of that removed while prototyping, and restored at the handoff.

## Context

- **«Дизайн» is the closest feature** (`kermanych/docs/specs/2026-10-29-design-tab.md`). A design
  is an ordinary `kind: "agent"` session with a marker, `designDir`. It is born from a cloud card
  (`design: true`) through `POST /sessions/from-task` → `SupervisorService.launchTask`
  (`supervisor.service.ts:1130`). Its first prompt is wrapped in the «Дизайнер» instruction in
  `openingPrompt` (`:1621-1637`). `DesignPage.vue` has a rail, the auto-started live preview
  (`ensurePreview`), the session browser `KBrowserPane` with ◎ «Вказати», and `KPanel` with the
  voice conversation (`useVoicePanel`). It builds an isolated prototype on `/__design/...` and
  takes 390/1280 screenshots after every change (`agents.ts:155-156`). Its handoff, «Задача →»,
  only files a card.
- **The preview and its tools require `kind === "agent"`**: `preview.service.ts:374`,
  `browser-mcp.service.ts:898,1092`, `KBrowserPane.vue:264`.
- **Launch.** `launch` (`:1450`) creates the worktree (`.gitworktree/<branch>`), copies carry
  files, then spawns through `withSlot` (the machine agent-slot queue) or `inSlot` (`direct`).
  `spawnLaunched` (`:1501`) spawns `omp --mode rpc` (`rpc-session.ts:51-77`). An empty
  `firstPrompt` leaves the child idle (`:1568-1572`), which costs no tokens. A session with no
  `taskId` is supported: it gets only the co-author directive (`:1563`).
- **Tools.** `launchToolsFor(kind)` (`chat-tools.ts:15`) gives `--tools read,grep,glob` to chats
  and reviews. The QA tester runs as a `review` child under that restriction and still calls MCP
  browser tools (`supervisor.service.ts:1881-1882`), so `--tools` does not hide the MCP bridge's
  tools [INFERENCE: from the tester working; verified in implementation]. A resumed child gets
  `launchToolsFor(s.kind)` too (`:3995`).
- **System prompt.** `systemAppendOpts(projectId, kind)` (`:1431`): language, docs policy,
  resources paragraph, `launchAppendFor(kind)`. It is applied on every spawn, resumes included.
- **Model and effort** come from the card or the project defaults
  (`SettingsPage.vue:315-325`) and can be changed live (`POST /sessions/:id/model`, `/effort`).
  `omp models` on this machine offers `claude-sonnet-5-5` (1M context, images, `low…max`) and
  `claude-haiku-5-5` (100K context).
- **Slots.** `withSlot` (`:650`) counts every `agent` session and parks a message or a launch
  while the machine's agent limit is reached.
- **Pointer.** ◎ picks collect in a per-session tray (`stores/browser.ts`). «Надіслати агенту»
  sends them with `useSendPicks` → `orchestrator.sendMessage`, composed by `composePicksMessage`
  and `picksImages` (`lib/browser-picks.ts`). Each pick carries the URL, selector, text, styles,
  `source {file, line, component}` and a crop.
- **Voice.** The voice conversation sends each delegated utterance with
  `orchestrator.sendMessage(…, { voice: true })` (`stores/voice.ts:195`). Picks are not
  attached.
- **Promotion.** `promoteChatToAgent` (`:1298`) turns a chat into an agent in place: the UI mints
  the card, the api links it and re-launches with a fork and the `promote` instruction.
- **Delete.** `deleteSession` (`:2944`) stops the child and the preview, removes the worktree and
  the local branch.

## Decisions

1. **The agent edits the real app code in the session's worktree; HMR shows it.** This covers
   both editing existing screens and building new pages: a new page is a new route in the real
   app, built from the project's kit, so it looks native from the start. The worktree branch
   isolates it until a PR.
   - Rejected: an isolated prototype route as in «Дизайн» (editing an existing page would mean
     copying it into the prototype). Rejected: DOM-only edits in the browser (instant, but gone on
     reload and the implementer gets no code).
2. **Frontend only; data is stubbed.** The prototyping agent hardcodes data next to the page or
   in one mock file, every stub marked with a `synergy-mock` comment. «Зберегти» buttons change
   local state only. It may read existing stores and API; it never adds endpoints, migrations or
   backend code. The implementer replaces every `synergy-mock`.
   - Rejected: a light backend (needs API restarts, no HMR; rewritten later anyway). Rejected:
     no limits (loses the speed).
3. **Model: `claude-sonnet-5-5`, effort `low` by default, chosen in the start form.** The form
   remembers the operator's last choice (`localStorage`). When the remembered or default model is
   missing from `GET /models`, the project default is used. The model can be switched live with
   the existing picker. «Імплементувати» runs on the project's default model and effort.
   Per-change latency is measured on this repository during implementation and recorded under
   «Verification».
   - Rejected: Haiku as default (100K context runs out on a large repository). Rejected: a project
     setting with a cloud column (speed is the operator's own preference; a migration for it is
     not warranted). Rejected: the project default with forced `low` (a heavy model stays slow).
4. **A checkpoint after every agent turn, and a step strip with «Повернутися сюди».** When a
   turn settles and the worktree has changes, the api commits all of it: subject
   `synergy: <request, first line, ≤ 72 chars>`, the full request in the body, `--no-verify` (a
   target project's commit hooks would cost the seconds this mode exists for). No model call. A
   turn with no changes makes no checkpoint. Restoring never rewrites history: it checks out
   that checkpoint's tree and commits it as `synergy: повернуто до кроку N`. Git is the only
   store: the strip and the chronology are read from `git log <base>..HEAD`. Restoring is refused
   while a turn runs.
   - Rejected: named variants as git branches (a tree UI, switching branches under a running
     dev server, picking a variant at the handoff; can be added later on top of the same
     checkpoints). Rejected: asking the agent to undo (slow, unreliable).
5. **One session type, two entry points, the agent starts idle.**
   - «Нова фіча»: topic (optional), base branch, model, effort.
   - «Змінити сторінку»: start path (e.g. `/users/42`), base branch, model, effort.
   - No card at launch: a new `POST /sessions/synergy`. Branch `synergy/<slug>` in its own
     worktree, slug from the topic, else from the path, else from the date and time. The name is
     the topic, else «Синергія: <path>», else «Синергія <date, time>».
   - The preview starts at once and opens on the start path. The omp child spawns with no
     opening prompt (idle, no tokens). The operator's first request is its first turn.
   - Every request carries the preview's current URL (decision 8).
   - The time of the first preview setup in a fresh worktree is measured during implementation
     and recorded.
   - Rejected: a card at launch with a `tasks.synergy` column (board noise from throwaway
     experiments; a migration). Rejected: no form (no base branch or model choice). Rejected:
     editing the operator's own checkout with their running dev server (no isolation; the
     preview's seeded api is not their real data).
6. **«Імплементувати»: the same session, branch and worktree; a fresh agent with a brief.**
   - The UI files a card (title = the session name, description = the brief, prefix `feature`,
     the operator as assignee), then calls `POST /sessions/:id/synergy/implement {taskId}`.
   - The api refuses while a turn runs or when there is no checkpoint. It stops the Sonnet child,
     clears `synergy`, `ompSessionFile`, sets `taskId`, the project's default model and effort,
     and spawns a fresh child in the existing worktree (no `git worktree add`, no new setup, the
     preview keeps running) through the slot queue, like any agent.
   - The opening prompt is the editable «Імплементувати Синергію» instruction around the brief:
     the chronology of requests without restored-away steps, the pages visited, the base branch;
     an instruction to read `git diff <base>...HEAD` and every `synergy-mock`, and to build it
     properly: backend, migrations, tests, i18n, docs, no stubs left. The diff is not pasted into
     the prompt: the agent reads it.
   - The session leaves «Синергія» and appears on «Агенти». PR and «Завершити» work as for any
     agent. The branch stays `synergy/<slug>`.
   - Fresh context, not a fork: the prototyping conversation is full of tries and rollbacks the
     implementer must not resurrect, and its tokens are waste.
   - Rejected: a new session on a `feature/` branch off the synergy branch (second worktree and
     setup, two branches to keep in sync). Rejected: a card only, as «Задача →» (the operator wants
     the handoff to start the work).
7. **Speed is enforced at launch, not asked for.**
   - Tools: `read`, `edit`, `write`, `grep`, `glob`, plus the Kermanych MCP browser tools and
     `preview_status` / `preview_logs`. No `bash`, no subagents. Applied on every spawn, resumes
     included (`launchToolsFor` decides by the session, not only its kind).
   - No skills overlay, no triggers, no docs-policy line in the system prompt.
   - The editable «Синергія» instruction goes into the system prompt append on every spawn,
     because the child starts with no opening prompt and must keep its role across resumes and
     `/compact`. It says: one change per turn; no tests, type checks, docs or commits (Kermanych
     checkpoints); frontend only with `synergy-mock` stubs; build from the project's kit; an
     ambiguous request is done the most likely way and named in one sentence, not asked about;
     screenshots and `preview_logs` only when the operator says something broke; reply in one or
     two sentences.
   - Rejected: instruction only with the full toolset (the model still runs tests "just in
     case").
8. **Picks and the current URL ride on every request.** For a Синергія session,
   `orchestrator.sendMessage` appends the tray's picks (text via `composePicksMessage`, crops via
   `picksImages`) and the preview's current URL to the message, then clears the tray. Typed
   messages, «Надіслати агенту» and the voice conversation all pass there, so «оце перемісти
   ліворуч» said by voice after a ◎ pick reaches the agent with the element. The voice
   conversation itself is unchanged.
   - Rejected: separate channels as now. Dictation into the composer is a separate task for all
     sessions.
9. **No slot queue; «Відкинути» deletes; desktop and browser platforms only.**
   - A Синергія session is not counted against the agent slots and never waits, on launch or on a
     message. After «Імплементувати» it is an ordinary agent and counts again.
   - «Відкинути» (with a confirmation) is the existing `DELETE /sessions/:id`: child, preview,
     worktree and the local `synergy/<slug>` branch go.
   - Several Синергія sessions may exist; the rail lists them. The idle child is reaped after
     15 minutes as any other and wakes on the next request.
   - The page works in the desktop app for projects whose platform has a browser
     (`platformHasBrowser`). The web build and other platforms show why it is unavailable.
   - Rejected: the shared queue (a busy machine would make the operator wait minutes) and keeping
     the branch on discard (local branches pile up; a prototype worth keeping is implemented).

## Changes

### Core (`packages/core`)
- `types.ts`: `Session.synergy?: { page?: string }` (start path for «Змінити сторінку»).
- `worktree-names.ts`: `"synergy"` in `BRANCH_PREFIXES`.
- `agents.ts`: `SYNERGY` (session) and `SYNERGY_IMPLEMENT` (session) entries in `AGENTS`, with
  ids `synergy` and `synergy-implement`; holes for the brief.
- New `synergy.ts`: the default model id, the checkpoint subject/body format and its parser, the
  chronology from a checkpoint log (restores drop the steps after their target), the brief.

### API (`apps/api`)
- `registry.service.ts`: additive columns `synergy INTEGER`, `synergy_page TEXT`; list mapping
  and insert.
- `sessions.controller.ts`: `POST /sessions/synergy {projectId, topic?, page?, base?, model?,
  effort?}`, `GET /sessions/:id/synergy/steps`, `POST /sessions/:id/synergy/restore {sha}`,
  `POST /sessions/:id/synergy/implement {taskId}`.
- `supervisor.service.ts`:
  - `createSynergy`: `resolveLaunchParams` with prefix `synergy`, `createSession`, `launch` with
    an empty first prompt;
  - `spawnLaunched` and the resume spawn: Синергія tool list, no skills/triggers overlay, the
    «Синергія» append instead of the docs-policy line;
  - `withSlot` / `slotCounts`: Синергія sessions are neither counted nor parked;
  - turn-settle hook → checkpoint commit; `synergySteps`, `restoreSynergy`, `implementSynergy`;
  - preview start opens the start path.
- `chat-tools.ts`: `launchToolsFor` takes the session; `SYNERGY_TOOLS`.
- `worktree.service.ts`: commit-all with `--no-verify`, log of checkpoints, restore-tree commit.

### UI (`apps/ui`)
- `router/routes.ts`, `layouts/MainLayout.vue`: route `synergy`, a `VIEWS` row next to «Дизайн»,
  the redirect of a selected Синергія session.
- New `pages/SynergyPage.vue` built from `DesignPage.vue`'s parts: rail, two start forms in a
  `KModal`, `KBrowserPane`, `KPanel` with voice, the checkpoint strip with «Повернутися сюди»,
  toolbar «Імплементувати» and «Відкинути». Every action uses `useAsyncAction` / `usePending`,
  the rail and strip use `useLoadPhase` + `KSkeleton` (AGENTS.md, README → Async states).
- `stores/orchestrator.ts`: the Синергія decoration in `sendMessage`; `createSynergy`,
  `synergySteps`, `restoreSynergy`, `implementSynergy`. `lib/api.ts` calls.
- `pages/AgentsPage.vue`: hide Синергія sessions; keep `synergy` out of the prefix picker.
- «ШІ-команда»: the two instructions in the catalogue (`lib/ai-team.ts`, `agent-about.ts`),
  not triggerable (`lib/settings.ts`).
- i18n `uk` / `en`: nav, page, forms, strip, actions, errors.

### Docs
- `kermanych/README.md`: a «Синергія» section next to «Designs».
